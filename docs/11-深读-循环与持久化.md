## 一、Codex 的循环：`needs_follow_up` 是两个条件的或

找了很久，循环不在 `codex_thread.rs` 也不在 `session/mod.rs`，在 `core/src/session/turn.rs`。核心是 `run_sampling_request` 的返回值：

```rust
// session/turn.rs:580-620（节选）
match sampling_request_result {
    Ok((sampling_request_output, sampling_request_input)) => {
        guardian_budget_compacted = false;
        let SamplingRequestResult {
            needs_follow_up: model_needs_follow_up,
            last_agent_message: sampling_request_last_agent_message,
        } = sampling_request_output;
        if model_needs_follow_up {
            sess.input_queue
                .accept_mailbox_delivery_for_current_turn(&sess.active_turn, &turn_context.sub_id)
                .await;
        }
        // ...
        let (has_pending_input, token_status) = async {
            let has_pending_input = sess.input_queue.has_pending_input(&sess.active_turn).await;
            let token_status = super::context_window::context_window_token_status(
                sess.as_ref(), turn_context.as_ref(),
            ).await;
            (has_pending_input, token_status)
        }.await;
        let needs_follow_up = model_needs_follow_up || has_pending_input;
        let token_limit_reached = token_status.token_limit_reached;

        super::async_compaction::maybe_start(
            &sess, &step_context, &world_state,
            if needs_follow_up { CompactionPhase::MidTurn } else { CompactionPhase::PostTurn },
            &cancellation_token, &token_status,
            client_session.turn_state_with_auth_owner(),
        )
```

四点：

1. **`needs_follow_up = model_needs_follow_up || has_pending_input`**。模型要调工具 → 继续；**用户在你跑的时候又发了消息 → 也继续**（同一轮，不是新一轮）。和 Pi 的 steering messages 是同一个设计，两家独立收敛。
2. **压缩分相位**：`MidTurn`（还要再请求一次，现在压最划算）vs `PostTurn`（这轮结束了，趁空闲压）。时机错了会切在工具调用与结果之间，API 直接 400。
3. **`guardian_budget_compacted` 标志**：压完再来一次，且只给一次机会——防止「压完还是超限」的死循环。
4. **`turn_diff_tracker`** 贯穿整轮：它记录这一轮改了哪些文件、改成了什么。我们只有一个 `changedFiles: string[]`，只有文件名没有内容，做不了撤销。

## 二、Kimi 的步进：每一步是一个状态机转移

`agent/loop/loopService.ts:975-1015` 是「下一步能不能走」的闸门：

```ts
const turn = this.active;
if (turn === undefined) return { type: 'fail' };
if (turn.controller.signal.aborted || machineSignal.aborted) return { type: 'fail' };
if (turn.stopRequested) return { type: 'fail' };
if (turn.failedStep !== undefined) return { type: 'fail' };
const consumed = this.mirrorConsumedNudges(turn);
if (turn.steerController.signal.aborted) { turn.steerController = new AbortController(); }
if (turn.toolStopRequested && consumed.live === 0) return { type: 'fail' };
const stepOrdinal = Math.max(this.engine?.currentStep() ?? 0, turn.steps + 1);
const maxSteps = this.config.get<LoopControl>(LOOP_CONTROL_SECTION)?.maxStepsPerTurn;
if (maxSteps !== undefined && maxSteps > 0 && stepOrdinal > maxSteps && !consumed.bypass) {
    turn.maxStepsError = createMaxStepsExceededError(maxSteps);
    return { type: 'fail' };
}
turn.steps = stepOrdinal;
turn.gatedSteps = stepOrdinal;
const step: MachineStepState = {
    number: stepOrdinal,
    uuid: randomUUID(),
    signal: turn.controller.signal,
    // ...
    pendingToolIds: new Set(),
    toolCallUuids: new Map(),
    resolvedToolIds: new Set(),
    toolStopTurn: false,
```

三个细节：

1. **`stepOrdinal = max(engine.currentStep(), turn.steps + 1)`**——序号不是本地自增计数器，是**从状态机读再取大**。为什么？因为恢复/重放时本地计数器会回来，状态机不会。恢复后的序号必须继续往上走，不能从 1 重来。
2. **多重终止条件**，每个都有独立语义：`aborted`（用户取消）、`stopRequested`（工具要求停）、`failedStep`（上一步失败了）、`toolStopRequested`（工具批被中止且没有还在跑的）、`maxSteps`（超预算）。我们只有一个「连续 3 次工具失败」+「maxSteps」。
3. **`pendingToolIds` / `toolCallUuids` / `resolvedToolIds` 三件套挂在 step 上**。每个人都在做**工具调用与结果的配对记账**。

## 三、三家都在解的那个问题：tool_call ↔ tool_result 配对

第三点是这轮最重要的发现。看三家的文件命名就知道：

| 项目 | 位置 | 干什么 |
|---|---|---|
| DSH | `packages/compaction/compaction/src/tool-pairing.ts` | 压缩时保证配对不被切开 |
| opencode | `session/runner/to-llm-message.ts` | 发请求前组装，顺带修复配对 |
| Kimi | `loopService.ts` 的 `pendingToolIds` / `resolvedToolIds` | 每步记账 |
| Codex | `stream_events_utils.rs` 的 `needs_follow_up` + `turn_diff_tracker` | 轮内账本 |

**为什么必须专门建模？** 因为主流 API 有硬约束：assistant 消息里出现的每个 `tool_call`，都必须有对应的 `tool` 角色消息；反过来，孤立的 `tool` 消息也会被拒。而**打断点恰恰落在配对中间**：

- 用户在工具执行到一半时点了取消 → assistant 有 3 个 tool_call，只回了 1 个结果
- 压缩把某个 tool_result 裁掉，但它的 tool_call 还在历史里
- 连续失败 3 次触发 abort → 最后一个 tool_call 没结果
- 会话恢复时文件只写了一半

任何一条都让下一次请求直接 **HTTP 400**，而且错误信息通常是 `messages with role 'tool' must be a response to a preceding message with 'tool_calls'` 之类，用户完全看不懂。

**我们的代码有这个 bug。** `loop.ts` 在 abort 和失败路径上直接结束，不补桩。而 opencode 的方案是发请求前统一跑一遍修复：

```ts
// 概念示意（opencode session/runner/to-llm-message.ts 的做法）
// 1. 扫历史，找出所有 assistant.tool_calls 的 id
// 2. 找出所有 tool 消息的 tool_call_id
// 3. 差集：有 call 没 result → 插入 "（已中断，未执行）" 的合成 tool 消息
// 4. 反向差集：有 result 没 call → 丢弃该 result
```

第 4 条容易漏：**孤立的 tool 消息同样要删**，不能只补不删。

## 四、Pi 的流式：用「占位消息」原地替换

`agent-loop.ts:383-470` 的 `streamAssistantResponse` 有个很干净的手法：先把一条 partial 消息**推进 context 数组**，之后每个增量事件都原地替换它。

```ts
case "start":
    partialMessage = event.partial;
    context.messages.push(partialMessage);   // ← 先占位
    addedPartial = true;
    await emit({ type: "message_start", message: { ...partialMessage } });
    break;

case "text_delta":
case "toolcall_delta":
    if (partialMessage) {
        partialMessage = event.partial;
        context.messages[context.messages.length - 1] = partialMessage;  // ← 原地换
        await emit({ type: "message_update", assistantMessageEvent: event, message: { ...partialMessage } });
    }
    break;

case "done":
case "error": {
    const finalMessage = await result();
    if (addedPartial) {
        context.messages[context.messages.length - 1] = finalMessage;  // ← 收尾替换
    } else {
        context.messages.push(finalMessage);
    }
```

好处是：**UI 永远看到的是同一个数组**，不需要第二套「临时消息」状态；`toolcall_delta`（参数分片流式）和文本增量共用一条路径。

我们不用流式（`requestUrl` 不支持），但恢复场景会用到同一个模式——恢复时先把 checkpoint 里的消息推进数组，再追加新的，索引不能错位。这一步我们目前是「先清空再重建」，恢复长会话时会闪一下。改成占位替换能消掉。

## 五、Pi 的 durable：先提交，再显示

`pi/packages/durable/README.md` 是这套代码里写得最好的一份设计文档，三句话概括它的承诺：

> **Conversations, model turns, tool calls, and your own state are committed to storage before anything is shown.** If the process dies mid-turn, reopening the storage picks the work up where it stopped.

### 5.1 提交顺序：先落盘，再渲染

不是「做完事情记个日志」，是「**日志没落盘，界面上什么都别出现**」。这样崩溃后的不变量是：界面上看到过的，磁盘上一定有；磁盘上有的，不一定显示过（可以重放）。

### 5.2 幂等靠 `requestId`，不靠去重表

```ts
const submission = await root.submit({ type: "input", content: "Hello", requestId: "greeting-1" });
// After a restart: the same request ID finds the same submission.
const again = await root.submit({ type: "input", content: "Hello", requestId: "greeting-1" });
// again.id === submission.id
```

崩溃恢复时最怕的不是「丢了一条消息」，是「不知道那条消息发出去没有」。用调用方提供的 `requestId` 做幂等键，重复提交返回同一条——**不需要查「我刚才是不是发过了」**。

### 5.3 存储后端的耐久性说得很精确

> SQLite: WAL mode with `synchronous = NORMAL`: **commits survive process crashes; the newest may be lost on power or host failure.**

这句话把「进程崩溃」和「断电」分成了两档保证。多数项目含混地用「持久化」一词把这两件事混在一起。

### 5.4 最关键的一句（对我们的意义）

> The portable SQLite and JSONL cores (`/storage/sqlite`, `/storage/jsonl`) **run without Node APIs**, for example on Bun or in Cloudflare Durable Objects, given an asynchronous `SqliteDatabase` facade **or a `FileSystem` from `@earendil-works/pi-durable/env`**.

**存储层抽象成 `FileSystem` 接口后，内核可以在没有 Node 的宿主里跑。** 这正是 Obsidian 插件的处境：没有 `fs`，只有 `vault.adapter`。他们要解决的约束和我们一模一样，而且解法就是把 IO 抽成注入的接口。

### 5.5 顺带一条：`sessionId` 不只是标识

> Each conversation has its own persisted UUIDv7 in `pi.provider`, forwarded to pi-ai as `sessionId` for **provider prompt-cache and session affinity**. It survives reopen, retries, reset, compaction, and model changes.

稳定的会话 id 送到 provider，能吃到**前缀缓存与会话亲和**。我们的 `makeRunId()` 每次 run 生成新 id，从没送给 API。DeepSeek/Kimi 都支持自动前缀缓存，但带上稳定 id 能让路由落在同一台机器上，命中率更高。

## 六、落到我们代码上：三个具体改动

### 6.1 修 tool_call/tool_result 配对（**bug，优先**）

`src/agent/loop.ts` 在发请求前加一步：

```ts
/** 修复 tool_call 与 tool_result 的配对，避免下一次请求 400。 */
function repairToolPairing(messages: ChatMessage[]): ChatMessage[] {
  const callIds = new Set<string>();
  for (const m of messages) {
    if (m.role === "assistant" && m.tool_calls) {
      for (const c of m.tool_calls) callIds.add(c.id);
    }
  }
  const answered = new Set<string>();
  for (const m of messages) {
    if (m.role === "tool" && m.tool_call_id) answered.add(m.tool_call_id);
  }
  const out: ChatMessage[] = [];
  for (const m of messages) {
    // 孤立的 tool 消息：丢弃
    if (m.role === "tool" && (!m.tool_call_id || !callIds.has(m.tool_call_id))) continue;
    out.push(m);
    // assistant 的调用没结果：紧跟其后补桩
    if (m.role === "assistant" && m.tool_calls) {
      for (const c of m.tool_calls) {
        if (!answered.has(c.id)) {
          out.push({ role: "tool", tool_call_id: c.id, content: "（已中断，该工具未执行）" });
          answered.add(c.id); // 避免重复补
        }
      }
    }
  }
  return out;
}
```

调用点：`provider.complete()` 之前，以及 `loadState()` 之后（恢复的会话可能就是从中间断的）。

### 6.2 `finishReason === "length"` 时整批判失败

Pi 的做法（`agent-loop.ts:264-270`）搬到 `loop.ts` 的工具批次处理处：如果这一轮 `finishReason === "length"`，不要解析参数，直接给每个 tool_call 回一条「输出被截断，参数不完整，请重试并减少输出或拆分操作」。

### 6.3 截断改外溢

`tools.ts` 现在超过 `MAX_OUTPUT_CHARS = 20_000` 直接切。改成：

```ts
if (result.length > MAX_INLINE_CHARS) {          // 默认 4000
  const rel = `spill/${runId}/step-${step}.txt`;
  await ctx.app.vault.adapter.write(`${baseDir}/${rel}`, result);  // 失败则退化为原样返回
  return `[结果 ${result.length} 字符，已存至 ${rel}]\n\n${result.slice(0, HEAD_CHARS)}\n\n…（可用 read_file 的 from/to 读取剩余部分）`;
}
```

写盘失败时**保留原结果**（DSH 的做法），不要因为存储故障把内容弄丢。

## 七、一句总结

10 篇的结论是「抄哪些原语」，11 篇的结论是：**这七家真正在拼的不是能力，是中断后的正确性。**

`needs_follow_up` 的或运算、`CompactionPhase::MidTurn`、`pendingToolIds`、`requestId` 幂等、commit-before-render、`FileSystem` 注入——六个看起来无关的机制，全都在回答同一个问题：**当执行在任意一点被切断时，怎么保证下一次还能继续且不重复副作用。**

我们是手机端插件，被切断的概率比桌面高一个数量级（切后台、锁屏、系统杀进程）。这个问题对我们比对他们更重要，而我们现在一条都没处理。

精确 → 忽略行尾空白 → 忽略首尾空白，三档逐级降级，但**每一档仍要求唯一**，不唯一就报错。文档里写了被替换的区间是**原文**区间（含全角空格），所以替换不会留下残渣。返回值多了一个 `matchedWith` 字段，模型能看出自己提供的文本和原文差在哪（Codex 的 `matchedWith` 同名设计）。

**6. P3 审批记忆** — 新增 [`src/agent/approvals.ts`](../src/agent/approvals.ts)。

原策略是「累计改满 N 个文件后，每次写都弹窗」。用户在同一个目录里改十篇要点十次——第二次之后他就不看 diff 了，闭眼点接受，比不弹更糟。现在：**批准一次，记住那个目录**，同一会话内直接放行。粒度选目录而不是单文件，因为真实意图通常是「这个文件夹你随便改」。想彻底关掉有隐私模式。

**7. 旁路提醒通道** — 新增 [`src/agent/reminder.ts`](../src/agent/reminder.ts)。

配对修复补桩后，模型并不知道「那些调用没生效」，可能顺着旧计划往下走。以前只能塞进 user 消息，模型会当成用户新指令。现在用 `<system-reminder>` 包起来，并在系统提示里声明它的性质（Claude Code / opencode 的同款做法）。

**8. P1 截断改外溢** — 新增 [`src/agent/spill.ts`](../src/agent/spill.ts)，在 `loop.ts` 的 `serializeForModel` 收口。

超过 4000 字符的工具结果写到 `.obsidian/plugins/obsidian-agent/spill/<runId>/`，上下文里只留「字符数 + 行数 + 落点 + 开头 1200 字符 + 分段读取示例」。三个细节：

- **`read_file` 不参与外溢**——它自己就有 `from/to`，再套一层只会让模型为了看中间段去读临时文件；
- **写盘失败退回原截断**——不能让存储故障把内容弄丢；
- **外溢目录在 `path.ts` 里单独放行**（否则 `read_file` 读不回来，外溢等于把内容丢了）；
- 插件启动时清理 7 天前的目录。

### 剩余

### 测试

`npm test` 共 196 个用例，分两层：

**纯逻辑单测**（122）：配对修复 7、敏感文件 6 组、模糊匹配 13、审批/提醒/外溢 11。

**集成测试**（12，`test/loop.integration.test.ts`）：把 `obsidian` 模块换成 [`test/mocks/obsidian.ts`](../test/mocks/obsidian.ts) 的最小实现，直接驱动真实的 `AgentLoop`。

mock 里有一条刻意的还原：**`.obsidian/` 下的文件不出现在 vault 索引中**。这正是「外溢文件读不回来」的根因——不还原这一点，测试就是绿色的谎言。

**测试有效性用变异验证过**：把 `read_file` 的外溢分支临时改回旧写法，外溢用例立刻变红；恢复后变绿。没有这一步，「43 个用例通过」只是个数字。

### 设备自检（真机 · 44 项）

单测和集成测试都活在 mock 里，真实 Obsidian 的 `adapter`、`.obsidian` 目录只能上机验。

触发方式刻意绕开了 UI：把 `selftest.flag` 放进插件目录 → 重载插件 → `onload` 检测到就自己跑剧本 → 写 `selftest-report.json`。

**为什么不用 adb 模拟点击**：Obsidian 是 WebView 应用，`adb shell input text` 只支持 ASCII（中文指令打不进去），无障碍树里输入框的 bounds 经常是错的（实测报 `[0,0][105,2608]`），盲点可能把字打进用户正在编辑的笔记里。自检不碰 UI，确定性高得多。

覆盖四层：工具层 10 项、序列化 3 项、循环层 6 项（含**崩溃恢复**——构造「2 个调用只回了 1 个结果」的存档，验补桩与提醒注入）、渲染层 1 项。

为了能测循环层，把 `serializeForModel` 从 Loop 的私有方法抽成了 [`src/agent/serialize.ts`](../src/agent/serialize.ts) 的独立函数：一个东西测不了，往往是它跟所在对象耦合太紧。

### 空回复不能当完成（14:36 事故复盘）

用户说「把 knowledge/tech 下每个 _index.md 最后加 `- review`」。模型读出 19 个文件，只读了 8 个就返回了**空消息**（无文字、无工具调用），循环把它当成「任务完成」，用户看到的是「共 3 步，修改 0 个文件」的静默失败。

三处修正：

1. **空回复不算完成**：第一次空 → 注入提醒重试一次；连续两次空 → `status=failed` 且错误信息说明原因。
2. **历史不再被污染**：`done` 事件的汇总行改用 `.oa-msg--summary` 样式；对话历史改从存档里取 [`finalAnswer()`](../src/agent/answer.ts)，不再从 DOM 抓（DOM 里混着汇总行）。
3. **「继续上个任务」真的续跑**：以前只有命令面板能续跑，聊天里说一句会开一个什么都不知道的新任务。现在 `wantsResume()` 命中「继续/接着/续上/continue」且有存档时，直接 `resume()`。

顺带补了**成功路径的运行汇总日志**——之前一次成功的运行一行日志都不留，出事只能靠存档倒推。

### 对话历史必须落盘（不是「先放着」）

第一版把 history 放在 `ChatView` 的内存字段里，理由听起来合理：面板开着就一直在。实际手机上重启是常态——改插件要重载、MIUI 随时回收、崩溃一次就归零。用户重开面板看到的是一片空白，问「对话历史都没有啊？」。

现在落盘到 `<插件目录>/chat-history.json`（[`src/agent/history.ts`](../src/agent/history.ts)）：

- 只存 user/assistant 纯文本，不存工具结果和运行汇总——够渲染，也够模型理解上下文
- 上限 100 条、单条 2000 字符
- 坏文件按空历史处理，不影响面板打开
- 面板打开时渲染回来并标一行「已载入 N 条历史」；有「清空」按钮同时清内存和磁盘

一个相关的坑：运行汇总行（「— 运行结束…」）和模型回答以前共用同一个 CSS 类，`querySelector(".oa-msg--assistant")` 抓到的其实是汇总行，历史全被它污染。现在汇总行有独立类 `.oa-msg--summary`，回答改从存档用 `finalAnswer()` 取。

### token 消耗实时显示

每轮模型调用后循环都会发一个 `usage` 事件（累计值），面板据此刷新一行小字：

```
0.013 Mb · 0.011↑ 0.0013↓
```

格式规则在 [`src/util/format.ts`](../src/util/format.ts)：`Mb` 是**百万 token**（不是 megabyte，token 不是字节）。小于 0.01 Mb 保留 4 位，1 Mb 以下 3 位，以上 2 位——手机状态行只有一条位置，精确到个位没人关心还占地方。

拆分显示故意只留一个 `Mb` 后缀，否则「0.011 Mb↑ 0.001 Mb↓」在小屏上会换行成两截。

### 准则下沉：从 prompt 到代码

`AI/00-总指令.md` 里那些「禁止修改 AI/00-06」「禁止修改 skills/」「首页/知识地图/任务看板 除非用户明确要求」，原本只是 prompt 里的一段文字。模型读得到，也会忘。现在分成两级落到代码：

| 级别 | 范围 | 行为 |
|---|---|---|
| deny | `AI/00-06`、`skills/**` | 直接抛错，没有覆盖通道 |
| confirm | 首页、知识地图、📋 任务看板、`templates/**` | 强制弹窗，不看文件数阈值、不吃审批记忆 |

后者刻意绕开了 `ApprovalStore`：如果用户的目录级审批把 `知识地图.md` 也放过去了，这条准则就形同虚设。

修改记录（第 4 条）也改由插件在任务结束时自动追加，一次任务一条而不是一次写入一条——批量改 19 个文件时记 19 条会把日志刷成垃圾。

### 多会话

`chat-history.json` 从平铺数组升级成 `{version:2, current, sessions[]}`，旧文件读进来会自动迁移成一个会话。每个会话带 `runId`，把它和运行存档绑起来，「继续执行」才知道该恢复哪一个——面板里点开某条历史会话，如果它还挂着未完成的存档，才会出现那个按钮。

### skill：把流程知识从代码里赶出去

准则、分类原则、命名规范、v3 流程这些是"知识"——会变，且只在特定任务里用到。塞进 system prompt 每轮都付费，写成工具又太死。所以做成 skill：

- `scanSkills()` 只读每个 md 的**前 2KB**，取 `name` + `description`；没有 frontmatter 就退化用 H1 当名字、第一段当描述（用户手写的 skill 大多没 frontmatter）
- 索引进 prompt，每个 skill 一行，实测 5 个 skill 只有 474 字符
- 正文等模型判断匹配后用 `use_skill` 读，一次 1534 字符——不匹配就一分钱不花

扫描范围只认 `skills/` 和 `AI/skills/`，别的目录里的 md 不会被误当成 skill（有对应用例盯着）。

### 语义层工具：shell 给不了的那部分

| 工具 | 靠什么 | 为什么全文 search 替代不了 |
|---|---|---|
| `search_by_tag` | `metadataCache.tags` | 查 `android` 能命中 `android/compose` 子标签；搜文本会漏、也会误命中 |
| `list_by_frontmatter` | `metadataCache.frontmatter` | 属性是结构不是文本，`status: active` 用 grep 会撞到正文里的同名词 |
| `move_note` | `fileManager.renameFile` | 搬文件的同时**改全库双链**；自己用 adapter.write + remove 会把所有 `[[链接]]` 指空 |

`move_note` 的自检一开始是失败的：我把临时文件放在了 `.obsidian/plugins/...` 下，而 `.obsidian/` 不被 vault 索引，`fileManager` 拿不到 TFile。这正好证明了它和 `read_file` 走的是两套体系——前者靠索引，后者靠 adapter。

### 工作记忆：把「不可跳过」变成真不可跳过

准则原文写着「Step 0 和 Step 4 不可跳过」，但那是写给模型看的——它会忘。所以拆成两半：

**读（自动）**：每轮开始读 04 的 `## 当前活跃任务` 和 05 的最后一条 `### ` 记录，塞进 system prompt。范围是刻意收窄的——04 里还有「待处理队列」「临时备注」，05 末尾还有「快速索引」表格，全塞进去每轮多烧几百 token 却跟当前任务无关。实测注入 1523 + 116 字符。

**写（工具）**：`record_memory` 按他们既有的字段模板写（`**完成时间**`／`**操作内容**`／`**对话时间**`／`**任务**`），插在正确位置：04 插在标题下（新的在上），05 插在「快速索引」之前。

**校验（提醒）**：任务结束时有文件改动、但 `appliedOps` 里既没有 04 也没有 05，就发一条状态提醒。插件不代替模型编内容——工作记忆写什么只有模型知道；但可以确保它「知道该写」。

一个必须说清的设计：`record_memory` **故意不走准则守卫**。04/05 在 `AI/` 下，守卫禁止模型改 00-06；但准则同时要求回写 04/05，两条规则在这里正撞。解法是这条写入由插件代劳、格式固定，而不是让模型自由发挥去改配置文件——和修改记录是同一个例外。

### 检查清单：只注入能判定的部分

01 和 02 都是 `- [ ]` 结构，直接可解析。但两份文件加起来 40+ 条，全塞进 prompt 每轮要多花上千字符——而「删除任务是否已确认」这类条目在整理笔记时根本不适用。

所以分开处理：

| | 注入方式 | 实测 |
|---|---|---|
| 01 任务前 | 只取「开始任务前」那一段（11 条），逐条列出 | 任务类型专属的「删除任务」等段落丢弃 |
| 02 任务后 | **只给 6 个分组名**（基础规范／目录规范／内容质量／链接与引用／索引更新／修改记录），细则用 `read_checklist` 按需取 | 全文 19 条，一个字都没进 prompt |

合计 356 字符。模型看到分组名就知道要核哪几块，真需要逐条对时再拉全文——和 skill 是同一个思路：索引常驻，正文按需。

这里也踩了个假绿：自检断言写的是 `prompt.includes("任务前")`，而块里的文案是「任务开始**前**逐项确认」——字符串对不上，报「检查清单没进 prompt」。代码是对的，断言是错的。改成断言完整文案 + `Step 3` 标记后通过。教训：断言要贴着真实文案写，别写同义词。

### 真机跑真实任务后暴露的五个问题

用户拿它整理 `cook`/`cooking` 两个目录，连跑四次（15:57 / 16:03 / 16:05 / 16:17），留下了完整证据：

| 现象 | 证据 | 处置 |
|---|---|---|
| skill 正文被外溢 | `spill/.../30-use_skill.txt`，模型又花一步读回来 | `use_skill`/`read_checklist` 加入外溢豁免 |
| 模型去 patch `AI/03` 被守卫拒 | 日志 1075 行 | system prompt 明说「03 由插件自动写」 |
| `backup/` 旧副本抢在正本前命中 | `cooking` 标签命中 `backup/Cook/火锅食材清单-20260818.md` | 搜索类工具统一排除 `backup/`、`.trash/`、`.obsidian/`、`_agent-selftest/` |
| 自检往用户记录里写 8 条垃圾 | `03-修改记录.md` 里 8 条「自检：…」 | 修复 + 手工清掉这 8 条 |
| 20 步上限撞墙却报「已完成」 | `state/...1605-h8ut.json` step=20 status=done | 撞上限时明确提示「说『继续』可接着跑」 |

第 4 条最值得记：自检是插件自己跑的，它写进用户文件的那一刻就成了污染源。凡是「插件自己的行为」都该和「用户的任务」隔离开——修改记录、记忆区、spill 目录都是这个道理。

### 删除：没有功能不是能力问题

准则写着「禁止删除笔记」，所以最初干脆没做删除工具。但真机上模型走到「剩下 3 份火锅清单涉及删除」就卡住了——它没有工具，只能把活推回给用户。

正确解法不是自由删除，而是**回收站语义**：
- `trash_note`：走 `fileManager.trashFile`（用户在 Obsidian 里设的系统回收站或 `.trash/`），不是 `adapter.remove` 那种物理删除
- `trash_folder`：非空文件夹必须显式 `recursive: true`，否则拒绝并报出里面有几项
- 确认框里带上**反向链接数**——准则 02 的「删除任务」要求先确认没有引用，这个数字直接摆在用户眼前
- 受保护路径（`AI/00-06`、`skills/`）仍然硬拒

### 移动端选中：Obsidian 把 user-select 关了

真机反馈「对话历史里的文字不能选中复制」。原因是 Obsidian 移动端在全局把 `user-select` 设成 `none`——正文阅读区它自己会打开，但插件的自定义视图不在它的白名单里，于是面板里一个字都选不中。

两件事一起做：

1. 自己的容器显式打开：`.oa-msg__body { user-select: text; -webkit-touch-callout: default }`
2. 每条消息配一个「复制」按钮——Android WebView 的长按选中在自定义视图里很不稳（有时只选中一个词、有时弹不出菜单），按钮是确定路径

`copyText()` 用 `navigator.clipboard` 优先、`document.execCommand("copy")` 兜底：前者在 WebView 里需要安全上下文，后者过时但在 WebView 里反而更可靠。复制成功会弹 Notice「已复制 790 字」，而不是只把按钮文案改一下——手机上按钮太小，光换字容易被忽略。

真机验证：点一下 → Notice 出现、按钮变「已复制」、MIUI 剪贴板事件 `eventType=CLIPBOARD` 上报。

### 流式：两条通道与一次诚实回退

最早这里只有 `requestUrl`——它走宿主进程，不受 WebView 的 CORS 限制，移动端最稳；代价是**拿不到流式**，只能等整段返回。所以早期版本点发送后就是长时间的「思考中」，然后一大段文字一次性出现。

现在加第二条通道 `chatStream()`：`fetch` + SSE，字一个个蹦。但它受 CORS 约束，所以策略是「能流则流」：

```
chatStream(fetch + SSE) ─失败且还没吐字─> chat(requestUrl 非流式)
                        └─已经吐过字─> 直接报错，不重发
```

最后那条分支是关键：**已经吐过字就不能退回非流式重发**，否则用户会看到前两句重复一遍。

三个易错点，各有一条测试：

| 坑 | 测试 |
|---|---|
| SSE 分块恰好切在 JSON 中间 | 每 5 字符切一刀，断言内容完整 |
| 工具调用参数分散在多个 delta 里 | 按 index 累积 id/name/arguments 再拼 |
| delta 与最终文本的顺序 | 断言所有 delta 都在 `assistant` 之前，面板才不会重复渲染 |

usage 也要靠 `stream_options: {include_usage: true}` 要在最后一个 chunk 里带——不发这个字段，面板的 token 计数在流式下会一直是 0。

中止（`中止` 按钮）以前只设一个标志位，要等当前请求自己结束；现在 `abort()` 直接 `controller.abort()` 掐断连接，SSE 读取立刻抛错退出。

### 一个被自检放过的真 bug：清单从来没进过 prompt

真机查 system prompt 才发现：真实任务里 `任务开始前逐项确认` 和 `Step 1` 都**不在** prompt 里。

根因是 `start()` 只读了 `skills` 和 `memory`，`checklists` 只在 `resume()` 里读。而自检走的那条路自己读了清单，所以全绿——**同一个功能，两条路径，一条通一条不通，测试恰好在通的那条上**。

这类 bug 的教训不是"多写测试"，而是：**测试要通过真实入口**。所以补了三条断言，一条在单测里（`loop.start()` 的 system prompt 必须含清单），一条在真机自检的「一轮完整执行」里（同一个入口），并把三份注入材料收成一个 `refreshContext()`，让 start/resume 无法再走岔。

### 记忆注入的副作用：模型会"接着做旧任务"

真机发一句 `reply with: ok`，模型没有回答，而是继续执行 04 里记着的「把 cooking 全部统一格式」，一口气读了 12 篇菜谱。

原因是「当前活跃任务」写得太像指令。修法是在记忆块开头加一句定位：这些是**背景**不是指令，用户这一轮说的话优先，无关就照这一轮做。

（顺带证明流式在这台机器上是通的：日志里连续 4 条 `流式调用成功：26 字符 / 2 个工具调用`，没有一条 `流式不可用`。fetch + SSE 在这个网关可用，不需要退回 requestUrl。）

### 让用户拍板：一个 `ask_user` 工具，而不是让模型自己写问句

最初的失败是：模型把「统一格式方案」写成一段漂亮的表格，然后自然结束。面板显示 `完成 · 9 步 · 改动 0 个文件`——它其实在等用户回话，但**从状态上看就是做完了**。用户只会想「跑了半天啥也没改」。

修法不是改文案，而是加一个硬工具 `ask_user`：

- 调用它 → `state.pendingQuestion = { text, options?, multiple? }`，状态切 `awaiting_confirm`，循环 `break`
- 面板把 `options` 渲染成按钮，**点一下就等于把那句话发给模型**（`sendText` 与输入框走同一条路）
- 不给 `options` 时退化成「在下面回一句」

为什么一定要选项：用户在**手机上**，打一句中文要切键盘、切输入法。`ask_user options` 让「全做 / 只改名 / 先改 3 个试试」变成一次点击。这条设计是照 `obsidian-yolo` 的 `ask_user_question` 抄的（它更全：多选 + 自动追加「其他」逃生口 + 一轮可问一组），我们只取了手机端收益最大的那半。

一个边界：`options` 只给 1 个是错误。一个选项等于命令，不需要问——工具直接返回错误，让模型改成 2 个以上或者别问。

### 上下文瘦身：先量，再决定信多少

动因很直接：真机一个「统一 15 篇菜谱格式」的任务，**9 步烧了 92405 prompt token**，10 步版是 148569。原因是每轮都把上下文重发一遍。

先按直觉做了「把老的工具结果换成占位」（`prune.ts`，幂等、只换内容不删消息、最近 4 条不动）。然后拿**真实跑完的那次任务**（`state/20261020-1722-u8ri.json`）算了一遍：

| 指标 | 实测 |
|---|---|
| 消息数 / 工具结果 | 78 / 58 |
| 上下文总字符 | 26156 |
| 被瘦身 | 4 条 |
| 省下 | 2536 字符（≈10%） |
| 折算最后一步 prompt | 148569 → 135005 |

**只有 10%，不是我原先估计的三分之二。** 原因在 `spill.ts`：`MAX_INLINE_CHARS = 4000`，超过 4k 字符的结果早就外溢到磁盘、上下文里只留一条摘要。所以「大结果不重发」这件事外溢机制已经在做了，`prune` 补的只是 800–4000 字符这一段（`list_files`、`search` 这类中等输出）。

结论：`prune` 留着（免费、安全、幂等），但它不是省钱主力。**真正的成本来自「步数 × 上下文」这个乘法**——10 步就是在同一份上下文上收 10 次费。要动就得动这一层（提示缓存 / 合并步骤 / 少读全文），而不是继续削单个结果。

顺带修掉一个语义坑：`usage.promptTokens` 是**十轮之和**，拿它当瘦身门槛会在第 2 步就误判。门槛改成 `contextSize(messages)`（当前上下文字符数 > 24000），语义直白也测得住。

### 两个被真机数据否掉的假设

省钱的直觉我连着错了两次，记下来比结论更有用。

**假设一：「老的工具结果占大头，瘦身能省三分之二。」**

拿真实跑完的那次任务算了一遍（78 条消息 / 58 条工具结果 / 上下文 26156 字符），只削掉 4 条、省 2536 字符，**约 10%**。原因是 `MAX_INLINE_CHARS = 4000`：超过 4k 的结果早就外溢到 `spill/`，上下文里只剩一条摘要。削单个结果这条路，外溢机制已经走完了。

**假设二：「15 个文件读了 10 步，做个批量读就能压到 3-4 步。」**

把那次任务的调用序列打出来看：

```
list_files → move_note ×11 → get_backlinks ×2 → read_file ×15 → patch_file ×23 → search ×2 → read_file ×3 → record_memory
```

**58 次调用，但只有 10 步。** 那 15 次 `read_file` 是**同一步里并发**的——模型本来就会在一轮里发多个工具调用。所以「一个文件一轮」根本不成立，批量读省的是消息条数，不是步数。

`read_files` 还是留着了（少 14 条消息、顺带强制「先读再改」），但它不是省钱杠杆。这一点必须在文档里写清楚，否则下次又会有人（包括我）照着一个错的前提去做优化。

**那钱到底花在哪？** 10 步 × 每步重发整份上下文。上下文从 ~4k 涨到 ~9k token，十步之和就是 148569。要动只能动这个乘法：

1. **提示缓存**——同一前缀重复发送，命中部分通常按 1/10 计价。这是唯一不牺牲能力的手段。
2. 步数本身——但真正的步数是 `move_note ×11`、`patch_file ×23` 这种「必要的活儿」，不是读取浪费。

所以这一轮我没再加工具，而是先加**观测**：解析 `prompt_tokens_details.cached_tokens`（OpenAI/DeepSeek 风格）和 `cache_read_input_tokens`（Anthropic 风格），日志里打 `（缓存命中 N）`，`Usage.cachedTokens` 也累加进 checkpoint。

下一次真实调用就能回答「这个网关到底缓不缓存」——**有数再决定要不要做 `cache_control`，而不是照着猜**。`readCached()` 对没报这个字段的服务端返回 `undefined` 而不是 0，就是为了不把「没报」误当成「没命中」。

### 缓存实测：网关一直在缓存，命中率 64% → 98%

上一条说「下一步是问网关支不支持提示缓存」。加了观测之后第一次真实调用就答了：

| 调用 | prompt token | 缓存命中 | 命中率 |
|---|---|---|---|
| 1 | 7508 | 4800 | 64% |
| 2 | 6317 | 4800 | 76% |
| 3 | 6763 | 6272 | 93% |
| 4 | 6866 | 6720 | 98% |
| 5 | 7109 | 6848 | 96% |

同一个任务内部，上下文前缀每轮都在复用，命中率从 64% 爬到 96%+；跨任务（换了话题）又回落到 64%——典型的自动前缀缓存行为。

结论：**不需要做 `cache_control`，网关（`api.llm.mioffice.cn` 后面的 glm 系模型）已经在服务端自动缓存**。这也解释了为什么 148569 个 prompt token 的任务实际账单没那么吓人。

所以我前面连着两轮的「省钱」焦虑，方向都不对：削结果（只值 10%）、合并步数（模型本来就会并发调用），而真正的大头早就被服务端拿走了。**先量再动手**这句话，这一轮用两次错估换了两次教训。

`Usage.cachedTokens` 现在会进 checkpoint，以后看单次任务的成本直接看这个字段，不用再从日志里抠。

### 选项卡片的端到端验证（真机）

网络恢复后补上了这一课，链路是真的通：

1. 发 `use ask_user to ask me 3 options about cooking style` → 模型调 `ask_user`，给 3 个烹饪风格选项 → 状态「等你回话」，卡片渲染出 3 个按钮
2. 用 `uiautomator dump` 拿到按钮坐标，`input tap` 点第 1 个（`硬菜宴客型：炖卤蒸烤齐上…`）
3. 下一轮的用户消息**就是这句话本身**（`state/*.json` 里第 6 条 user 消息），模型据此继续：读 `knowledge/life/cooking/_index.md` → `patch_file` 写进一行
   `> 偏好：硬菜宴客型——炖卤蒸烤齐上、工序多但撑场面，周末做` → 4 步结束，改动 1 个文件

面板上「点一个就行；想改方案也可以直接在下面打字」这句提示也在，用户想改方案直接打字即可，两种入口都留着。

一个操作上的坑：`uiautomator dump` 拿到的坐标和真正 tap 之间如果面板发生滚动（追加消息会滚），点击就会落到别的按钮上。第一次验证时正好落在相邻选项上，看起来像「点错了」。要稳定复现就把 dump 和 tap 放进同一条命令里，中间不要有人类操作。

### 真机自检抓到的一个 UI 真 bug：`disabled` 不能写字符串

多选分支写完，顺手在真机自检里加了一段：渲染一张 `multiple: true` 的卡片 → 断言「提交」初始禁用 → 点一个选项 → 断言变成启用且显示「提交（1）」。

第一次跑就红：**选了之后「提交」还是禁用的**。

原因：

```ts
submitBtn.setAttr("disabled", picked.size === 0 ? "true" : "false");
```

`disabled` 是布尔属性，HTML 只看它**在不在**，不看值——`disabled="false"` 依然禁用。所以多选卡片永远提交不了，用户只能一个一个点（点了也不发）。

修法是走 DOM property：`submitBtn.disabled = picked.size === 0`。

这类 bug 单测抓不到（没有 DOM），纯看代码也容易滑过去（`"false"` 读起来像「没禁用」），只有真的在 DOM 上点一下才会露。又一次说明：**面板这块必须真机点**。

### 那条天天刷的假警报：「改了 N 个文件，但没回写 04/05」

真机日志里每次任务结束都跟着一条：

```
WARN 改了 1 个文件，但没回写 04/05（准则 Step 4）。需要的话用 record_memory 补一条。
```

可模型明明写了——`AI/04-临时工作记忆区.md` 里那一段「烹饪偏好：硬菜宴客型」就在，时间戳和任务结束时间差 5 秒。

根因在判定的数据源：守卫看的是 `state.appliedOps`，而 `appliedOps` 只统计 `WRITE_TOOLS` 里的工具（`patch_file` / `create_note` / `write_file`）。`record_memory` **故意**不在里面——写 04/05 是插件的记账行为，混进去会让「改动 N 个文件」虚高。于是它就永远看不见「其实已经记过了」。

修法不是把那句警告删掉（它确实有用），而是给「记过了」一个独立的信号：

- `ToolContext.markMemory()` → `state.memoryWritten = true`
- 守卫改成 `if (!wroteMemory && !touched.has(04) && !touched.has(05))`

顺手还修出两个同类问题：

1. **`move_note` / `trash_note` / `trash_folder` 压根没算改动。** 昨天那次任务「11 次 move_note、23 次 patch_file」，AI/03 里只记了内容改动，11 次移动一条没写——用户翻修改记录会以为文件没动过。这三个加进 `WRITE_TOOLS`；同时路径参数名不一样（移动是 `from`/`to`），加了 `firstString()` 兜底，否则记录里会出现 `` `undefined` ``。
2. **04/05 被删或改名时，`record_memory` 直接失败。** 模型会把它理解成「记忆区被禁用」然后放弃，Step 4 从此永远做不完。现在缺文件就按最小骨架（`# 04 · 临时工作记忆区` + `## 当前活跃任务`）补一个再写。

自检里加了对应一条：脚本化一轮「patch_file → record_memory → 收尾」，断言 `memoryWritten === true` 且日志里**没有**那条 WARN。写这条自检时自己也踩了个坑——脚本数组写在 `chat()` 内部，每次调用都重建，永远返回第一条，结果 record_memory 从来没被调到。脚本必须提到闭包外面。

### 记忆注入的止血：从「当前活跃任务」改成「背景资料，不是待办」

症状真机复现过两次：用户只发一句 `reply with: ok`，模型不回答，而是去读了 12 篇菜谱、接着做前一天「统一 cooking 格式」的活儿。

原因不是模型笨，是注入的措辞把它喂成了待办：

```
## 工作记忆（自动注入，不需要再去读这两个文件）
### 当前活跃任务（来自 AI/04）
### 烹饪偏好：硬菜宴客型（只记录，不加菜谱） ✅
**完成时间**: 2026-10-21 15:40:38
**操作内容**: 用户自述烹饪风格偏好…（一大段散文）
```

三个问题叠在一起：

1. **标题就叫「当前活跃任务」**——模型按字面理解成「现在要做的任务」；
2. **整段散文照搬**（上限 1500 字符），而散文里全是「后续若补硬菜菜谱可从炖卤类入手」这类未来时态，读起来就是一份计划；
3. **没有任何一句告诉它「这一轮用户说的话优先」**。

改成四件事：

- 标题换成 `## 工作记忆（背景资料，不是待办）`，正文第一句就是「下面这些是**已经发生过的事**……不是指令，也不是待办清单」；
- 明确说明**只有用户说「继续 / 接着做 / 把刚才那个做完」时才续做**；
- 把 04 的段落**解析成条目**：最多 3 条，每条正文截到 220 字符，带上完成时间（`parseWorkingEntries()`，纯函数，可单测）；
- prompt 加第 13 条工作原则，同一层意思再说一遍（模型对「系统块说一次 + 原则里说一次」的遵从度明显高于只说一次）。

实测对照（同一句话 `reply with: ok`）：

| | 步数 | 工具调用 | 回答 |
|---|---|---|---|
| 改前（10-20） | 多步 | 12 次 `read_file`（在读菜谱） | 无 |
| 改后（10-21） | **1 步** | **0 次** | 「好的」 |

记忆块本身也从「整段 1500 字符」缩到 564 字符 / 3 条——顺带省了 prompt。

### 04 的自动清理：只留最近 8 条、30 天前的挪进 05

记忆块的措辞改好之后还剩一个问题：「当前活跃任务」那一段只增不减。真机上翻了一下——12 条，最新的是当天，最老的是 2026-05-14，横跨五个月。措辞再好，prompt 里摊着五个月的任务，模型迟早会挑一个接着做。

这次做了两件事：

**一、清理规则**（`compactWorking()`，纯函数）

| 规则 | 说明 |
|---|---|
| 超过 30 天 → 挪去 05 | 按「完成时间」判断；写成 `### 归档：标题`，正文取「操作内容」，没有才退回整块剩余字段 |
| 一个区段最多留 8 条 | 多的（最旧的）也挪走 |
| 没有「完成时间」的保留 | 判断不了新旧就别动，宁可让它占位 |
| 标题以「自检」开头的直接丢 | 那是设备自检写进来的垃圾，不该进用户的历史 |
| 当前活跃任务 + 已完成任务都清 | 只清前一个的话，老任务换个区段继续躺着 |

真机效果：`04` 从 6761 字节 / 12 条 → **5452 字节 / 5 条**，日志 `04 清理：挪 7 条老任务到 05`，7 条全部落进 05（`归档：` 条目 24 → 31）。「边界约定」「待处理队列」「临时备注」一个字没动。

**二、自检不再往用户记忆区写垃圾**

上一轮加的自检会真的调用 `record_memory`，于是把 3 条「自检记账」写进了用户的 `AI/04`。这条修了两头：自检现在**先备份 04/05、跑完写回**；清理逻辑也会把「自检」开头的条目直接丢掉（双保险）。

顺带发现一个真实缺陷：原来的区段边界只认第一个 `## `，「已完成任务」整段落在处理范围外——也就是说老任务根本没机会被清。改成按「当前活跃任务 / 已完成任务」两个区段各自处理，并且**从后往前改**（否则前一处改写会让后面的偏移失效）。

### 历史里那三段一模一样的话：回答取错了范围

翻真机上的 `chat-history.json` 时看到的：同一个 410 字的回答连着出现三次。一开始以为是面板重复渲染，看了代码才知道是**回答的归属错了**。

`finalAnswer(state)` 从 `state.messages` 尾部往前找第一条非空 assistant 内容——但 `state.messages` 的前半截是**注入的对话历史**。于是：

| 场景 | 结果 |
|---|---|
| 本轮模型只调了工具、没说话（比如 `ask_user` 暂停） | 找不到本轮内容 → 一路扫到历史里 → 把**上一轮**的回答当成本轮回答 |
| 面板拿到这个"回答" | 又存进历史一份 |
| 下一次同类运行 | 再存一份 → 三段一样的话 |

修法是给存档加一个 `turnStart`（本轮用户那句话在 `messages` 里的下标），`finalAnswer` 只在这个下标之后找。旧存档没有这个字段就退回老行为，不影响「继续执行」。

真机验证：清掉 4 组重复配对后重新对话，`turnStart=11`，注入的 10 条历史一条不重复，模型照样能答出「上次只改了 1 个文件」——说明上下文没被清坏。

### 按字符预算瘦身，而不是按条数

面板上原来只有 `MAX_HISTORY = 12`（条数）。问题是**一条可能是 2000 字的表格总结**。真机上量的：system prompt 3440 字 + 历史 2518 字，模型干活的空间被挤掉一半。

`src/agent/trim.ts` 里两条规则：

| 规则 | 为什么 |
|---|---|
| 单条超过 1200 字 → 留头 800 + 留尾 300 + 标「中间省略 N 字」 | 结论通常在开头，要求通常在结尾 |
| 总预算 4000 字 → 从最新往旧装，装不下就**整条丢**最旧的 | 半条拼接会让模型看到残句；必须连续，不能跳过中间去拿更旧的 |
| 留下来的第一条不能是 assistant | 否则模型在"自言自语" |

真机压测（往历史里塞 8 组 1700 字的假对话，共 26 条 / 29936 字符）：

```
历史瘦身：12 条 → 2 条，保留 2232 字符（丢 10 条最旧的，长的已截断）
```

实际发出去的 prompt 是 6344 token；不瘦身的话光历史就 29936 字符（约 1.5 万 token）。两层各司其职：面板的 12 条挡住"条数爆炸"，字符预算挡住"单条爆炸"。

（压测完把历史原样还原了，`chat-history.json` 与压测前逐字节一致。）

### 那个「永不触发」的剪枝门槛

原打算把 `CONTEXT_CHARS_GATE` 从 24000 降到 16000「看看会不会触发」。先量了再动手，结论有点难堪：

| 量什么 | 结果 |
|---|---|
| 真机 63 个存档的上下文大小 | 中位数 **4641** 字符，最大 31277 |
| 超过 16000 的存档 | 8 个，**全部**是加这个功能之前的（20261020） |
| 日志里 `上下文瘦身` 的出现次数 | 17 次，**全是 `[自检]`**，真实任务 0 次 |
| 存档里带「已省略」标记的 | 0 个 |

也就是说：门槛 24000 在真实使用里等于永不触发，只有自检能碰到它。降到 16000 是必要的，但**只降门槛不够**——真机一跑又暴露第二层问题：

一次 `read_files` 把 16 个文件塞进**一个**工具结果（11918 字符），而剪枝保护「最近 4 条结果」。结果数只有 2 条，全在保护范围内，门槛降到多少都剪不动。

于是改了两处：

| 改动 | 原因 |
|---|---|
| 保护粒度从「最近 4 条结果」改成「最近 2 批」 | 「批」= 一次工具调用带回来的那串结果；大批读取合并后按条数保护等于不保护 |
| 加 `worthPruning`：省不到 1500 字符就不动 | 占位本身也要花 token，剪三条各 900 字符的结果省 1980，不划算 |

真机验证（真实任务，不是自检）：

```
上下文瘦身：2 条工具结果改成占位，省 5322 字符（上下文 19868）
上下文瘦身：1 条工具结果改成占位，省 4083 字符（上下文 17012）
```

那是个「把 interview 下 5 篇逐个读一遍并各写一句」的任务，6 步跑完。检查了两件事：每个文件只读了一次（没有因为占位而重读），最后的 5 条摘要齐全——剪掉的都是模型已经消化过、可以随时重读的老结果。

还有一个反例值得记：同一批实验里让模型「读三个目录的所有文件」，上下文 37648 字符但**没有剪**——因为只有两批结果，全在保护范围内。这不是漏剪，是设计上不该剪：它正在用那批内容作答。

### 「本轮改动」卡片：为什么它没有折叠

手机上跑完一个任务，原来只有一行「— 运行结束，共 3 步，修改 1 个文件」。改了哪几个、每个动了几行、是新写还是覆盖，全在模型的话里，滚上去才看得到。

`src/agent/changes.ts` 把 `appliedOps` 变成可读结构：

| 工具 | 标签 | 说明 |
|---|---|---|
| `patch_file` | 改 | `+2 −1 行` |
| `create_note` | 新建 | `12 字` |
| `write_file` | 写入 | `12 字` |
| `move_note` | 移动 | `a.md → b.md` |
| `trash_note` / `trash_folder` | 删除 | 移入回收站 |

同一个文件被改三次只出一行（`groupChanges` 按路径归并），标题则按动作统计：`3 个文件 · 改 2 / 新建 1`。真机验证：

```
本轮改动 · 1 个文件 · 改 1
改  +1 −1 行
_agent-selftest/card-demo.md
```

**这个卡片原本可以点标题折叠，现在没有——因为点不动。**

排查顺序和证据：

| 尝试 | 结果 |
|---|---|
| `div` + `click` | 点了没反应，日志里没有处理函数的痕迹 |
| 换成 `<button>`（面板里能点的就是 button） | 一样没反应 |
| 加 `pointerdown` + 把结果写进标题文字 | 标题没变，说明事件根本没到元素 |
| 按 uiautomator 报的坐标点四次（1560/1570/1600/1650） | 全无反应 |

最后在 dump 里看到原因：卡片的 bounds 是 `[1551,1686]`，而状态行 `完成 · 3 步 · 改动 1 个文件` 的 bounds 是 `[1608,1668]`——两者重叠。滚动区里的元素报的是「内容坐标」，被固定的状态栏那一层压住了，触摸落不进去。

所以选择去掉折叠而不是硬修：一个点不动的按钮比没有按钮更糟。信息本身照样显示——卡片默认就是展开的。

### skill 对齐 agentskills.io：认新布局，不砸旧文件

规范要求的其实是三件事：

| 规范 | 原来的加载器 |
|---|---|
| 一个 skill 一个目录，入口是 `<目录>/SKILL.md` | 只认 `skills/` 下任意 `.md`，`SKILL.md` 会被当成名字叫「SKILL」的 skill |
| frontmatter 必填 `name` + `description`，`name` 只允许小写字母/数字/连字符，且等于目录名 | 单个正则 `^key:\s*(.+)$`，`description: >` 折叠写法读出来是 `>` |
| 可选 `license` / `allowed-tools` | 完全不读 |

改法是把 frontmatter 换成一个小 YAML 子集解析器（引号、`|`/`>` 块、行内数组），并且：规范布局用目录名兜底、旧布局照样能用、不合规只记 `warnings`。

真机上量了一下：库里的 5 个 skill **全部**不合规——中文名字 + 平铺文件。所以最终只有警告，没有改名：

```
skill 规范检查：5/5 个待整理 — Obsidian 到 Lark 文档导出（name「Obsidian 到 Lark 文档导出」
不符合规范（只允许小写字母、数字、连字符），建议改成 obsidian-to-lark）；…
```

建议的 slug 不是简单把名字转写。`slugify` 会把「Obsidian知识库管理」压成 `obsidian`，信息全丢；所以优先取文件名里更完整的英文（`skill-obsidian-knowledge-management` → `obsidian-knowledge-management`），并剥掉排序前缀 `000-` 和 `skill-`。

没自动迁移的原因写在下一节。

**没做的事：没动用户的文件。** `skills/` 是 MiClaude 在同步的目录，平铺 `.md` 是它的约定。为了"符合规范"把 5 个文件搬进 5 个目录，可能直接把这个同步弄断——而用户明天要用的不是规范，是能用的 skill。所以这里只做「认新、容旧、报差异」。
