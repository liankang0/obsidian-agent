# 02 架构设计

## 1. 分层

```
┌─────────────────────────────────────────────┐
│  UI 层        ChatView / DiffModal / 设置页  │
├─────────────────────────────────────────────┤
│  会话层       AgentLoop（多轮 + 工具调度）    │
│               └─ Checkpoint（运行状态持久化） │
├─────────────────────────────────────────────┤
│  工具层       tools.ts：read/patch/search/…  │
│               └─ 护栏：路径、范围、确认       │
├─────────────────────────────────────────────┤
│  存储层       app.vault.adapter / metadataCache
│               app.workspace / app.commands   │
├─────────────────────────────────────────────┤
│  模型层       provider.ts（OpenAI 兼容）      │
└─────────────────────────────────────────────┘
```

关键点：**会话层不直接碰 Vault**，所有文件副作用都经过工具层，这样护栏只需在一处实现。

## 2. 模块职责

| 模块 | 职责 | 不做 |
|---|---|---|
| `main.ts` | 注册视图、命令、设置页；持有 Loop 实例 | 业务逻辑 |
| `agent/loop.ts` | 组装消息、调用模型、执行工具、落 checkpoint | 具体文件操作 |
| `agent/tools.ts` | 工具 schema + 执行 + 护栏 | 网络请求 |
| `agent/provider.ts` | HTTP、鉴权、响应解析、错误归一化 | 重试策略（在 loop） |
| `util/path.ts` | 路径规范化、越界拦截、敏感目录判定 | 文件读写 |
| `util/log.ts` | 环形缓冲 + 落盘 | 上报 |

## 3. 一次 run 的时序

```
用户输入
  → loop: 组装 system + history + user
  → provider.chat()            ── HTTP ──▶ 模型
  ◀── assistant.content / tool_calls
  → 若有 tool_calls：
      逐个 executeTool()
        → 校验参数 → 读/写 → 返回结果（截断）
        → 高风险操作：暂停，等 DiffModal 结果
      → 结果作为 tool 消息回灌
      → 写 checkpoint
      → 回到 provider.chat()
  → 无 tool_calls：结束，展示正文
```

停止条件（任一命中）：无工具调用、达到 `maxSteps`、用户中止、连续 3 次工具失败。

## 4. Checkpoint 设计

**为什么必须做**：Android 会杀后台，一个 8 步的 run 在第 5 步被杀，如果状态只在内存里，用户看到的是「笔记改了一半、对话没了」。

存放位置：`<vault>/.obsidian/plugins/local-vault-agent/state/<runId>.json`

```jsonc
{
  "runId": "20261020-1132-a1b2",
  "createdAt": 1760938321000,
  "updatedAt": 1760938412000,
  "status": "running",          // running | awaiting_confirm | done | failed | aborted
  "step": 4,
  "maxSteps": 20,
  "messages": [ /* 完整消息数组 */ ],
  "pendingToolCall": { "id": "...", "name": "patch_file", "args": {} },
  "appliedOps": [               // 已执行的副作用，用于幂等与回滚提示
    { "tool": "patch_file", "path": "读书/xx.md", "at": 1760938400000 }
  ],
  "usage": { "promptTokens": 12000, "completionTokens": 800 }
}
```

状态机：

```
running ──需要确认──▶ awaiting_confirm ──接受──▶ running
   │                        └──拒绝──▶ running（回灌「用户拒绝」）
   ├──完成──▶ done
   ├──异常──▶ failed
   └──用户中止──▶ aborted
```

启动时扫描 `state/`，存在 `running` / `awaiting_confirm` 的记录就提示「继续上次任务 / 放弃」。**不自动续跑**——静默执行副作用比中断更危险。

### 4.1 撤销本轮（按修改记录逆向回放）

`appliedOps` 不只用于幂等提示，也是「撤销本轮」的数据源（WP3）：

- **采集**：`patch_file` / `write_file` / `create_note` 成功时，工具手里本来就有改前/改后文本，顺手挂到 `appliedOps` 的 `undo` 字段随 checkpoint 落盘。单侧超过 `UNDO_TEXT_CAP`（50k 字符）不留——宁可不可撤销，也不拿截断文本「还原」。
- **回放**：`undo.ts` 按路径分组、逆序模拟回放；回放前逐文件校验（patch 的 new 必须在当前内容中出现且仅出现一次；write/create 要求当前内容与改后版本逐字节一致），任何一条不满足就**整个文件跳过并逐条说明**，绝不产生半撤销状态。
- **落盘**：校验全过后每个文件只写一次（`vault.process` 原子写）；「新建」的撤销 = 内容一致时移入回收站，不做硬删除。
- **取舍**：只保证内容级还原，不保证元数据还原——移动、删除不走这条路径（移动过的路径、本轮删除过的文件直接跳过并说明），仍由回收站负责（见 ADR-010）。

## 5. 与编辑器的冲突

用户可能一边让 agent 改，一边自己在编辑器里改同一篇。三种情况：

| 情况 | 处理 |
|---|---|
| 文件未打开 | `vault.process(file, fn)` 原子读改写 |
| 文件在编辑器打开 | 仍走 `vault.process()`；手机上面板是活跃视图，`editor` 分支不可达，已删除 |
| run 期间用户手动保存了 | `vault.process` 会拿到最新内容再替换，替换失败（目标文本已变）就报错回灌 |

`patch_file` 必须校验「目标文本唯一命中」，命中 0 次或多次都失败——这是防止误改的核心手段。

## 6. 错误分类

| 类型 | 例子 | 策略 |
|---|---|---|
| 网络瞬时 | 超时、连接重置 | 重试 2 次，指数退避（1s / 3s） |
| 鉴权 | 401 / 403 | 立即失败，提示检查 Key |
| 限流 | 429 | 退避 10s，最多 3 次 |
| 请求非法 | 400（模型不支持 tools、超长） | 立即失败，提示换模型 |
| 工具错误 | 文件不存在、patch 未命中 | **不回失败，作为 tool 消息回灌**，让模型自己修正 |
| 内部 bug | 未捕获异常 | 记日志 + 中止 run + 保留 checkpoint |

「工具错误回灌」是关键设计：模型看到 `No unique match for patch in 读书/xx.md` 通常会自己重试成别的写法，比直接报错给人有用得多。但同一工具连续失败 3 次就中止，防止死循环烧 token。

## 7. 上下文预算

手机上不要指望长上下文。策略：

- 读文件默认整篇，但超过 `2000` 行强制要求给行区间
- 单次工具返回超过 `20000` 字符截断，并在末尾标注「已截断，剩余 N 字符」
- 检索结果最多 `20` 条、每条最多 `200` 字预览
- 历史消息超过 `30` 条时，把早期对话用一次摘要替换（v0.3 再做，MVP 先限制轮数）

## 8. 为什么不用 MCP

MCP 在这个场景里解决的是「让外部客户端访问 Obsidian」，而本项目是「在 Obsidian 内部跑 agent」。引入 MCP 只会多一层 IPC，手机上更是没有成熟的 MCP 客户端生态。**插件内直接调用 API 是最短路径。**
