## 一、Pi —— 双层循环与三个细节

`packages/agent/src/agent-loop.ts:163` 的 `runLoop` 是七家里最好读的循环，因为作者刻意让它不依赖任何 UI。

```ts
// agent-loop.ts:178-183
// Outer loop: continues when queued follow-up messages arrive after agent would stop
while (true) {
    let hasMoreToolCalls = true;
    // Inner loop: process tool calls and steering messages
    while (hasMoreToolCalls || pendingMessages.length > 0) {
```

三层结构值得注意：

1. **外层循环的用途不是步数，而是「排队消息」**。用户在 agent 跑的过程中打字，消息进入 `pendingMessages`（"steering messages"），在下一轮模型调用前插入。所以外层 `while(true)` 的退出条件是"没有新消息了"，不是"步数用完了"——**Pi 根本没有步数上限**。
2. **`stopReason === "length"` 时把整批工具调用全部判失败**（`agent-loop.ts:264-270`）：

```ts
// A "length" stop means the output was cut off by the token limit, so
// every tool call in the message may carry truncated arguments. Fail
// them all instead of executing potentially borked calls.
const executedToolBatch =
    message.stopReason === "length"
        ? await failToolCallsFromTruncatedMessage(toolCalls, emit)
        : await executeToolCalls(currentContext, message, config, signal, emit);
```

这是个很容易漏掉的边界：**输出被 token 上限截断时，工具参数是不完整的 JSON**。执行它等于掷骰子。我们的 `safeParseArgs` 遇到坏 JSON 只返回 `{}`，然后工具报"参数缺失"——模型会以为是路径写错，反复重试，浪费三轮。应该直接告诉它"输出被截断了"。

3. **压缩挂在 `prepareNextTurn` 钩子上**（`agent-loop.ts:186`，注释明说 "Preparation can be long-running (for example, compaction)"）。压缩不是循环里的一个 if 分支，而是一个可替换的钩子。

> 对我们的意义：`length` 截断保护今天就能加，5 行代码。双层循环不要抄——手机插件没有"边跑边输入"的交互预算。

## 二、opencode —— plan 模式是插件，只读靠规则不靠提示词

`packages/core/src/plugin/plan.ts`（120 行）是我见过写得最完整的"只读模式"实现。它做了四件事：

**1. 只读由权限规则强制**（`plan.ts:38-47`）：

```ts
item.permissions.push({ action: "question", resource: "*", effect: "allow" })
item.permissions.push({ action: "edit", resource: "*", effect: "deny" })
item.permissions.push({ action: "edit", resource: path.join(directory, "*"), effect: "allow" })
```

注意第三条：`~/.opencode/plan/` 下**允许写**。plan 模式不是"什么都不能写"，而是"只能写计划文件"。这个区分比一刀切实用。

**2. 被拒绝时改写错误文案**（`plan.ts:50-58`）：

```ts
if (!(event.error.error instanceof Permission.BlockedError)) return Effect.void
event.error = new ToolFailure({
  message: `Cannot use ${event.tool} to modify files outside the Plan directory: ${directory}`,
})
```

原始错误是"Permission denied"，模型看不懂；改写后它知道"我在 plan 模式，只能写那个目录"。

**3. 提醒会对账**（`plan.ts:60-83`）——这是最容易被忽略的一条：

```ts
// Compaction and committed reverts can strip reminders while the session's agent stays
// put. Reconcile per request, appending near the tail so the cached prefix stays warm.
const missing = event.agent === plan && reminder !== enterReminder
```

**压缩会把 `<system-reminder>` 吃掉**，而 session 的 agent 还是 plan。所以必须每轮检查提醒还在不在，不在就在**用户最后一条消息之前**补回去（位置也讲究：和切换 agent 时的插入点对齐，且靠近尾部以保住前缀缓存）。

**4. 权限模型本身**（`packages/core/src/permission.ts`）：

```ts
export { Rule, Ruleset } from "@opencode/schema/permission"
const missingAgentPermissions: Permission.Ruleset = [{ action: "*", resource: "*", effect: "deny" }]
// ...
if (denied(input, rules)) return { effect: "deny" as const, rules }
```

三条设计：
- 规则是 `{ action, resource, effect }` 三元组，`resource` 支持通配。
- **deny 优先于 allow**（先判 `denied()`），不是"后写的覆盖先写的"。
- **没有声明权限的 agent 默认全拒**（fail-closed），不是默认全放。

还有个细节：拒绝不是只有"是/否"，还有 `CorrectedError`（带 `feedback` 字段）——用户可以说"别改那个，改成改这个"，反馈直接回流给模型。

**压缩参数**（`session/compaction.ts:37-46`）：

```ts
export type Settings = {
  auto: boolean
  /** Tokens kept free below the model's limits before compacting. Unset keeps 15%, and at least 16k, free. */
  buffer?: number
  /** Tokens of recent conversation kept verbatim beside the summary. */
  keep: number
}
```

三种触发原因：`auto`（预估超限）、`overflow`（provider 真的报超长）、`manual`（用户 `/compact`）。**`overflow` 是独立触发源**——不赌预估准确，等真实报错再压。

> 对我们的意义：plan 模式的三层（规则 deny + 错误改写 + 提醒对账）都要抄，尤其是提醒对账——我们的 checkpoint 恢复本质上就是"上下文被换掉了，但模式还在"，同一个坑。

## 三、Codex —— 两个可复用原语

### 3.1 execpolicy：策略是 Starlark，且自带单元测试

`codex-rs/execpolicy/README.md`：

```starlark
prefix_rule(
    pattern = ["cmd", ["alt1", "alt2"]], # ordered tokens; list entries denote alternatives
    decision = "prompt",                 # allow | prompt | forbidden; defaults to allow
    justification = "explain why this rule exists",
    match = [["cmd", "alt1"], "cmd alt2"],           # examples that must match this rule
    not_match = [["cmd", "oops"], "cmd alt3"],       # examples that must not match this rule
)
```

四个设计点，逐条对我们是可搬的：

| 设计 | 为什么重要 |
|---|---|
| `decision` 三值 `allow / prompt / forbidden` | 不是布尔。我们的确认是"要确认/不要确认"两档，缺"直接禁止"这一档 |
| `justification` | **审批弹窗里能显示理由**。用户看到"因为这条命令会删文件"比看到"是否允许？"好判断得多 |
| `match` / `not_match` **加载时校验** | 策略文件自己就是测试用例。写错规则会在加载时报错，而不是在 runtime 悄悄放行 |
| `host_executable` | 防御 basename 伪装：`/tmp/git` 不该匹配 `git` 的规则 |

### 3.2 apply-patch：模糊匹配三级降级

`codex-rs/apply-patch/src/seek_sequence.rs:1-60`：

```rust
/// Attempt to find the sequence of `pattern` lines within `lines` beginning at or after `start`.
/// ... Matches are attempted with decreasing strictness: exact match, then ignoring trailing
/// whitespace, then ignoring leading and trailing whitespace. When `eof` is true, we first try
/// starting at the end-of-file ...
```

三级降级 + EOF 锚定。这直接打在我们 `patch_file` 的痛点上：**我们现在的策略是"精确匹配失败就报错，让模型重读"**，而真实失败原因往往是不可见的空白差异（复制粘贴带出来的尾随空格、中文输入法的全角空格、CRLF）。

一次失败的代价是：模型重读整篇 → 重新生成 old → 再试。三轮 token 白烧。

Codex 的办法是：降级匹配，但**要求降级后仍然唯一**。我们的 `countOccurrences` 已经保证了唯一性，加降级是安全的。

> 对我们的意义：`patch_file` 加三级匹配并回报 `matchedWith: exact | trailing | trimmed`，让模型知道"这次是靠宽容匹配过的，下次注意格式"。比报错重试省一半 token。

## 四、DSH —— 最值钱的一条：别裁，外溢

### 4.1 我们之前以为的最优解是裁剪

`packages/compaction/compaction-tool-result-pruner/src/config.ts:6-11`：

```ts
/** Fixed marker substituted for every removed middle span. */
export const PRUNE_MARKER = '\n\n[... tool result middle pruned ...]\n\n'

/** Low-friction defaults for coding-agent tool output. */
export const DEFAULTS: ResolvedConfig = deepFreeze({
  thresholdChars: 8192,
  headChars: 4096,
  tailChars: 1024,
})
```

超过 8192 字符 → 保留头 4096 + 尾 1024，中间换成 marker。设计上有两个「正确」：**replay-safe**（幂等，改的是投影不是存储）、**model-free**（不调模型摘要，纯确定性）。按 Unicode code point 切，不切碎代理对。

### 4.2 但 DSH 自己还有更好的方案：spill

`packages/spill/README.md`：

> The `spill/` group stores full text outside the model's context and returns a locator with retrieval guidance. ... Tool-result spilling is opt-in through `maxInlineTokens` and **keeps the original result on storage failure**.

三个子包分工：`spill/`（存储服务）、`spill-local/`（本地文件后端）、`spill-policy/`（工具结果策略）。

**这比裁剪强，而且强得不是一点：**

| | 裁剪 | 外溢 |
|---|---|---|
| 信息 | 永久丢失中间段 | 全文在磁盘，可按需再取 |
| 模型行为 | 只能重跑工具 | 用 `read_file` 精确取需要的部分 |
| 失败模式 | 无 | 存储失败时**保留原结果**，退化成不裁剪 |
| 二次成本 | 重跑工具（可能很贵） | 一次文件读 |

对我们尤其合适：我们已经有 `read_file(from, to)`，**locator 天然可读**。「完整结果 3.2 万字符，已存到 `spill/20251020-a3f2/step7.txt`，可分段读取」——模型完全能自己决定要不要读、读哪段。

### 4.3 包分解的启发

58 个包，与内核直接相关的：`core`、`session`、`llm`、`interaction`、`guard`、`sandbox`、`shell`、`subagent`、`plan`、`goal`、`todo`、`workflow`、`compaction`(5 个子包)、`spill`、`context`、`credentials`、`deliverables`。

注意 `guard` 与 `sandbox` 是**两个包**：前者是策略（该不该做），后者是隔离（做了也翻不出天）。这个区分我们的 `path.ts` 没做——它同时负责"安全判断"和"路径规范化"，应该拆。

> 对我们的意义：**把 `MAX_OUTPUT_CHARS` 的截断改成 spill**。这是本次分析里唯一一条我建议直接推翻原设计的。

## 五、Kimi Code —— 内核分解的教科书

`packages/agent-core-v2/src/` 的目录树本身就是一张架构图：

```
agent/
  loop/                 ← 循环，内部还有 machine/（状态机）+ storeJournal（事件日志）
  permissionGate/       ← 闸门：放行/询问/拒绝的执行点
  permissionMode/       ← 模式：default / plan / auto …
  permissionPolicy/     ← 策略：policies/ 下十个策略文件
  permissionRules/      ← 规则：matchesRule.ts
  fullCompaction/       ← 整段压缩
  contextMemory/        ← 记忆
  contextProjector/     ← 上下文投影（压缩后的视图重建）
  interruptionReminder/ ← 中断提醒
  agentsMdReminder/     ← AGENTS.md 提醒
  modeMutex/            ← 模式互斥
  llmRequester/         ← 模型请求
tool/
  toolContract.ts  args-validator.ts  input-schema.ts
  path-access.ts   rule-match.ts      output-accumulator.ts
```

**权限拆成四个概念**（gate / mode / policy / rules），这是我这轮最大的认知修正：我们只有"一个 `confirm()` 回调 + 一个 `readOnly` 布尔"，它把这个空间拆成了：

- **mode**：当前处于什么模式（决定哪些 policy 生效）
- **policy**：一组有序判断函数，各自返回 `approve / ask / deny / 弃权`
- **rules**：用户配置的具体规则（路径、命令前缀）
- **gate**：真正执行"拦下来问用户"的那一层

`permissionPolicy/policies/` 下的十个文件，逐个都是独立关注点：

| 文件 | 职责 |
|---|---|
| `default-tool-approve.ts` | 默认工具直接过 |
| `fallback-ask.ts` | **兜底：没人管就问** |
| `dangerous-command-ask.ts` | 危险命令要问 |
| `sensitive-file-access-ask.ts` | 敏感文件要问 |
| `git-control-path-access-ask.ts` | git 控制路径要问 |
| `git-cwd-write-approve.ts` | 写工作目录直接过 |
| `auto-mode-approve.ts` / `auto-mode-ask-user-question-deny.ts` | 自动模式的两种取向 |
| `session-approval-history.ts` | 本次会话已批准过的，记住别重复问 |

「已批准过就记住」这条特别实用——我们的设计里没有，用户改十篇笔记要确认十次，第一次之后就不耐烦了。

### 5.1 敏感文件名单（我们漏掉的漏洞）

`tool/path-access.ts:18-46`：

```ts
const SENSITIVE_BASENAMES = new Set<string>([
  '.env', 'id_rsa', 'id_ed25519', 'id_ecdsa', 'credentials',
])
const SENSITIVE_PATH_SUFFIXES = [ ['.aws', 'credentials'], ['.gcp', 'credentials'] ]
const ENV_PREFIX = '.env.'
const ENV_EXEMPTIONS = new Set<string>(['.env.example', '.env.sample', '.env.template'])
export const SENSITIVE_DOT_VARIANT_SUFFIXES = [
  '.bak', '.backup', '.copy', '.disabled', '.key', '.old', '.orig', '.pem', '.save', '.tmp',
] as const
```

**注意最后那个数组**：`.env.bak`、`.env.key`、`.env.old`、`.env.pem` —— 改个后缀就能绕过朴素的黑名单。这个"点变体"处理是真正的攻击面思维。

对照我们：`path.ts` 只挡了 `.obsidian/`、`.git/`、`.trash/`。如果用户的 vault 里有一个 `服务器/credentials.json` 或 `keys/id_rsa`，我们的 `read_file` 会**原样发给模型 API**。这是真实的数据外泄路径。

> 对我们的意义：敏感文件名单必须补，且必须覆盖点变体。这一条优先级最高——它是安全问题，不是体验问题。

## 六、ZCode —— 把架构约束变成可执行文件

`architecture-policy.yaml`（节选）：

```yaml
version: 1
modules:
  - id: session
    roots: [packages/services/src/session]
    managed: false                      # 存量模块先标 legacy
    requires: [shared]                  # 只允许依赖这些模块
    publicEntrypoints:                  # 只有这些文件可被跨模块 import
      - packages/services/src/session/contract.ts
      - packages/services/src/session/taskIndexRepo.ts
  - id: storage
    roots: [packages/services/src/storage]
    managed: true                       # 新模块，受完整约束
    requires: [shared, rpc, services]
    publicEntrypoints: [packages/services/src/storage/contract.ts]
    layers: {domain: domain, app: app, adapters: adapters}
    layerOrder: [domain, app, adapters] # 层内依赖方向
    owner: desktop-settings             # 责任人
```

五个字段各自解决一个问题：

| 字段 | 解决的问题 |
|---|---|
| `roots` | 模块的物理边界在哪 |
| `requires` | 允许依赖谁（**白名单**，不是黑名单） |
| `publicEntrypoints` | 哪些文件是公开 API（其余视为私有） |
| `layers` + `layerOrder` | 模块内部的层次与依赖方向 |
| `managed: false` | **存量代码的豁免开关**——不给新代码，只给老代码 |

最后一条是关键工程智慧：新规则上马时，存量代码几乎必然违规。要么全改（不可能），要么规则形同虚设。它选了第三条：**标记豁免，新代码必须合规**。

还有 `owner`——每条边界有责任人。架构腐化最常见的原因不是没人懂规则，是没人认领。

> 对我们的意义：我们只有 9 个源文件、一个人维护，完整版用不上。但可以写成一份 30 行的 `architecture.json`，只检查三条：`tools.ts` 不许 import `main.ts`、`agent/*` 不许 import `ui/*`、`util/*` 不许 import `agent/*`。二十行脚本，`npm run check` 里跑。

## 七、Claude Code（闭源，仅有二进制证据）

二进制里能 strings 出系统提示词片段（`claude.exe`，2.8 亿字节）：

- `"You are an interactive CLI tool that helps users with software engineering tasks. You should work proactively and autonomously, executing immediately and minimizing interruptions."`
- 反过度设计条款：`"Don't add features, refactor, or introduce abstractions beyond what the task requires. A bug fix doesn't need surrounding cleanup; a one-shot operation doesn't need a helper. Don't design for hypothetical future requirements"`
- 工具结果处理：`"Tool results and user messages may include <system-reminder> or other tags. Tags contain information from the system. They bear no direct relation to the specific tool results or user messages in which they appear."`

最后这条印证了 opencode 的做法：**`<system-reminder>` 是独立于内容的旁路通道**，用来注入模式、提醒、告警，且明确告诉模型"这些标签不是用户说的"。我们目前没有任何旁路通道——所有上下文都是 user/assistant/tool 三种角色，想加个"注意：这是 plan 模式"只能塞进 user 消息里，模型会以为是用户的要求。

## 八、五个可复用原语（按优先级）

| # | 原语 | 出处 | 落地点 |
|---|---|---|---|
| **P1** | **大结果外溢，不裁剪** | DSH `spill/` | `tools.ts` 的 `MAX_OUTPUT_CHARS` 分支 → 写 `spill/<runId>/step-N.txt`，返回头部 + locator（默认 `maxInlineTokens: 2000`） |
| **P2** | **敏感文件名 + 点变体** | Kimi `tool/path-access.ts` | `util/path.ts` 加 `SENSITIVE_BASENAMES` / 点变体后缀，读和写都拦 |
| **P3** | **策略化确认（规则 + 理由 + 自测）** | Codex `execpolicy` + Kimi `permissionPolicy/policies/` | `tools.ts` 的 `mustConfirm` → `policy.ts`，规则 `{tool, pathGlob, decision: allow\|ask\|deny, reason}`，加载时用样例自检 |
| **P4** | **三级模糊匹配** | Codex `seek_sequence.rs` | `patch_file`：exact → rstrip → trim，回报 `matchedWith` |
| **P5** | **截断输出保护** | Pi `agent-loop.ts:264` | `loop.ts`：`finishReason === "length"` 时整批工具调用判失败，明确告知模型 |

顺带两条低成本改进：
- **`<system-reminder>` 旁路通道**（Claude/opencode）：给 `ChatMessage` 加一个不进正文的 system 注入点。
- **会话内审批记忆**（Kimi `session-approval-history.ts`）：同一次 run 里批准过的路径前缀，下次直接放行。

## 九、结论

1. **`spill` 取代 prune，是本轮唯一的方案级修正。** 我此前在 09 篇推荐"工具结果裁剪"，DSH 自己的代码表明它还有更好的下一层。裁剪是止损，外溢是保本。
2. **权限不是一个布尔，是四个概念**（mode / policy / rules / gate）。我们的 `readOnly` + `confirm()` 是这套东西的最小退化形态，够用但不该再往里堆 `if`。
3. **护栏的价值不在"写得严"，在"可被测试"**。Codex 的 `match`/`not_match` 自测、ZCode 的 `managed: false` 豁免、Kimi 的十个独立 policy 文件——共同点是**规则是可枚举、可单测、可逐条审的对象**，不是散落在业务流程里的判断。
4. **最该先做的是 P2（敏感文件名单）**，因为它不是体验问题。其余四条都能等，这条不能。
