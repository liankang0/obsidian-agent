# 08 架构决策记录（ADR）

格式：一条决策一段，包含「背景 / 决策 / 后果 / 替代方案」。追加式，不删除旧决策（推翻时新增一条并标注 supersedes）。

---

## ADR-001 做成 Obsidian 插件，而不是独立 Android App

**背景**：独立 App 要访问 Vault 必须解决分区存储权限。可选 `MANAGE_EXTERNAL_STORAGE`（需用户去设置页手动授权、上架要申报豁免）或 SAF（无真实路径，需自写 VFS）。

**决策**：做插件。

**后果**：
- 权限问题消失，`app.vault.adapter` 直接读写
- 免费获得 `metadataCache`（frontmatter/标签/双链）
- 一套代码覆盖 Android/iOS/桌面
- 代价：无 Node.js，不能用 shell/git/rg；受 Obsidian API 稳定性约束

**替代方案**：Termux 内跑 CLI agent（可行但环境脆弱，不适合日常）；独立 App + SAF（工程量大 3～5 倍）。

---

## ADR-002 不做 shell、不接 Claude Code / Codex

**背景**：手机端插件环境没有 `child_process`，无法启动任何本地进程。

**决策**：接受这个约束，工具集只覆盖 Vault 操作 + HTTP。

**后果**：
- 无法做 `git` 提交、无法用 `ripgrep` 加速检索
- 换来的是：状态简单、无外部依赖、可预测
- 「批量重构代码」类需求不在范围内

**替代方案**：把重活放电脑端 Claude Code，Vault 通过 Syncthing 同步（本项目不承担）。

---

## ADR-003 MVP 不做流式输出

**背景**：`requestUrl` 不支持流式；`fetch` 流式受 CORS 限制，未验证。

**决策**：先非流式，用状态行补偿体验。

**后果**：
- 长回答需要干等，但工具调用期间有明确进度提示
- 架构上预留 `provider.chatStream()` 接口，后续可切换

**替代方案**：一开始就做 `fetch` 流式——风险是某些端点直接不可用，导致返工。

---

## ADR-004 `patch_file` 优先于 `write_file`

**背景**：整篇重写会：① 消耗大量 token；② 容易在无关处引入改动；③ 一旦模型幻觉就整篇丢。

**决策**：默认提供 `patch_file`（精确唯一替换），`write_file` 标为高危、需确认。

**后果**：
- token 成本显著下降
- 改动可解释（diff 是局部的）
- 需要处理换行归一化、唯一性校验、未命中的错误回灌

**替代方案**：只给 `write_file`——实现简单，但不可接受误改风险。

---

## ADR-005 每步落 checkpoint，重启后手动续跑

**背景**：Android 杀后台概率高，长 run 必然被打断。

**决策**：每完成一次工具调用就写 `state/<runId>.json`；重启不自动恢复，只提示。

**后果**：
- 需要工具幂等（重放不能写坏）
- 用户多一次点击，但避免「静默执行副作用」

**替代方案**：内存态 + 失败重来（体验差）；前台 Service（插件做不到）。

---

## ADR-006 不做全库 embedding，MVP 用关键词检索

**背景**：手机算力与电量不适合建全库向量索引；Obsidian 插件内也缺少成熟的本地 embedding 运行时。

**决策**：`search` 用子串/正则遍历；向量检索留到 M3 且只对子集。

**后果**：
- 检索质量弱于语义检索，但足够覆盖「按 tag / 按标题 / 按关键词」的常见需求
- 大库遍历慢，需要加时间预算与并发

**替代方案**：借 Copilot 的 Vault QA 做语义检索（但那是「问」不是「改」，不能代替）。

---

## ADR-007 长期记忆做成 4 类有界文件

**背景**：借鉴 Mobie CC。无限增长的记忆会反噬：占用 context、互相矛盾、无法审计。

**决策**：`Profile`（目标）/ `Style`（表达偏好）/ `WorkMode`（协作方式）/ `Vault`（库约定），每类 ≤ 8 KB，写入前先出候选让用户确认。

**后果**：
- 记忆可读、可删、可版本对比
- 需要实现「压缩重写」逻辑（超限时让模型自己精简）

**替代方案**：把历史对话全塞进 context（成本线性增长，最终不可用）。

---

## ADR-008 只做单个 Vault、单用户

**背景**：Obsidian 插件天然按 Vault 加载；用户只有一个人。

**决策**：不设计多租户、不做跨 Vault 访问、不做权限体系。

**后果**：`state/`、`logs/`、记忆文件全部落在当前 Vault 的插件目录下，天然隔离。

**替代方案**：无。这是刻意放弃的通用性。

---

## ADR-009 流式输出已实现（取代 ADR-003）

**背景**：ADR-003 决定 MVP 不做流式，理由是 `requestUrl` 不支持流式、`fetch` 流式受 CORS 限制未验证。真机迭代中用 `fetch` + SSE 打通了流式，且验证了受限端点可自动回退非流式。

**决策**：流式作为默认路径（`provider.chatStream()`）；流不可用或首包前失败时自动回退非流式（已吐过字则不回退，避免内容重复）。配套收口网络语义：非流式整段超时与流式空闲超时分开（长生成只要还在吐数据就不掐），中止后绝不重试、晚到的增量丢弃。

**后果**：
- 长回答逐步可见，不再干等；超时语义可配置（`requestTimeoutMs`，默认 90s）
- 中止语义复杂度由 provider/loop 承担（有测试钉住），不外溢到 UI

**取代**：ADR-003 的「先非流式」按此处执行；其中「架构上预留 `chatStream()` 接口」已兑现。
