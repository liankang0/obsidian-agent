# 01 需求与场景

## 1. 背景

日常在手机上用 Obsidian 记录：通勤时语音速记、读书记录划线、随手写日报。问题不在于「记录」，而在于**记录之后的整理**——这些动作都需要遍历多篇笔记、按规则改写，手动做一次要十几分钟，而在手机小屏上做尤其痛苦。

已有的 AI 插件（Copilot、Text Generator 等）主要解决「围绕当前这篇笔记对话」，不解决「按指令批量改库」。而电脑上的 Claude Code / aider 能改库，却没法和手机上的 Obsidian 共存。

**本项目要补的就是这一段：在手机上，用自然语言驱动对 Vault 的结构化修改。**

## 2. 用户与约束

- 用户：单人（作者自己），不对外分发，不考虑多租户、权限体系
- 设备：Android 手机（主力），桌面端作为开发与调试环境
- 网络：国内网络，模型走国内直连 API（DeepSeek / Kimi 等）
- 时间：碎片化，单次交互最好在 1～3 分钟内出结果

这些约束推导出三条硬性设计原则：

1. **不依赖外网稳定性** → 不用需要代理的官方端点，不引入额外的中转服务
2. **不能等待太长** → 单次任务控制在若干步内；长任务必须可中断、可续跑
3. **不能悄悄改坏东西** → 所有写回都要能看到 diff、能撤销

## 3. 核心场景

### 场景 A：批量归一化（最高频）

> 「把 `读书/` 下所有笔记的 tag 统一成 `#book`，并按 `作者/年份` 补 frontmatter」

- 涉及 10～100 个文件
- 操作高度规则化，用脚本更快，但手机上没法跑脚本
- 成功标准：改完能在文件列表里看到，且旧值可追溯

### 场景 B：把散落素材合成一篇（最有价值）

> 「把这周记在 `速记/` 里的 6 条内容，整理成一篇 `周报/2026-W42.md`，按项目分组，保留原文链接」

- 需要跨文件读取 + 理解 + 生成
- 这是纯 LLM 的强项，也是手动做最费时的
- 成功标准：生成的新笔记有双链回原文，内容不失真

### 场景 C：单篇深改（最常用）

> 「这篇写得太散了，帮我重组结构，论点保留，把重复的段落合并」

- 只动一篇，但要求精确
- 成功标准：diff 可读，能逐块接受/拒绝

### 反例（明确不做）

- ❌ 全库问答 / 知识库 RAG 客服（Copilot 已做得很好，重复造没意义）
- ❌ 代码重构（Vault 里没有代码项目，需要 shell 的场景直接不碰）
- ❌ 联网调研（有网页工具但不作为核心，模型自带联网能力更省事）
- ❌ 多端实时协作

## 4. MVP 范围

只做「能在手机上可靠地完成场景 A 和 C」。

| 能力 | MVP | 后续 |
|---|---|---|
| 读单篇 / 读片段（行区间） | ✅ | |
| 精确替换（patch） | ✅ | |
| 新建笔记 | ✅ | |
| 全库关键词检索 | ✅ | 语义检索（v0.3） |
| frontmatter / 双链读取 | ✅ | |
| diff 确认 | ✅ | 分块接受（v0.2） |
| checkpoint 续跑 | ✅ | |
| 批量任务（一次改多文件） | 半自动（逐个确认） | 批量模式（v0.2） |
| 长期记忆 | | v0.3 |
| 流式输出 | 不做 | 视 CORS 实测（v0.2） |
| 语音输入 | 用系统输入法 | |

## 5. 验收标准

MVP 完成的判定（全部满足才算）：

1. 手机上一次完整 run 能改 3 个文件，中途锁屏杀进程后能续跑
2. 任何一次写回都先出现 diff，拒绝后文件完全不变
3. 模型提出越界路径（`../`、`.obsidian/`）时被拦截并回灌错误
4. 单次 run 的 token 成本可控：读文件有行数上限，检索有结果上限
5. 出错时能在 `<plugin>/logs/` 里找到可读的原因（不是只有 `undefined`）

## 6. 非功能需求

- **可恢复**：任何时刻杀进程，重启后状态一致
- **可审计**：每次写回留痕（谁改的、改了什么、什么时候）
- **可降级**：模型不支持工具调用时，退化成「生成文本让我自己贴」
- **低成本**：日常使用月成本控制在个位数人民币（用 DeepSeek 类模型）
