# 05 竞品分析与取舍

## 1. 全景

| 产品 | 形态 | 强项 | 短板（相对本项目） |
|---|---|---|---|
| **Copilot for Obsidian** | 开源插件 | 全库问答（Vault QA）、多 provider、成熟 | 偏「对话」；批量改库弱；手机端体验一般 |
| **Smart Composer** | 开源插件 | 类 Cursor：工具调用 + diff 确认，架构最接近 | 桌面为主；手机上用得少 |
| **Text Generator** | 开源插件 | 模板化批量生成 | 以「生成」为主，不做结构化改库 |
| **Smart Connections** | 开源插件 | 本地 embedding、语义关联 | 是检索器不是 agent；手机建索引重 |
| **Mobie CC** | **闭源商业插件** | 移动优先、候选+diff、4 类有界记忆、隐私模式 | 闭源、绑安装 ID、¥99、无源码、无批量 |
| **Claude Code / aider** | 命令行 | 真·工具链（shell/git/rg）、能跑长任务 | 手机上不可用（Termux 勉强） |
| **本项目** | 自用插件 | 完全可控、可批量、无授权 | 只有一个人维护，功能少 |

## 2. Mobie CC 深读

它是最有价值的对照物，因为它证明了两件事，也暴露了三个取舍。

### 它证明的

1. **插件内跑 agent 在手机上是可行的**——不是理论，是已发布的产品
2. **「候选 + diff + 确认」是移动端写回的正确形态**——不是直接调用 `write_file`

### 它暴露的取舍

**取舍一：用「有界记忆文件」替代向量检索**

它维护 Profile / Style / Work Mode / Vault 四类记忆文件，都强调 *bounded*。这是在手机算力约束下的合理妥协：不建全库 embedding，靠「小而稳的长期记忆 + 关键词检索」达到 80% 的效果。

对我们的启示：**MVP 不要做 RAG**。先跑通「检索 + 记忆」，等真的觉得不够再加向量。

**取舍二：定位「知识 agent」而非「编码 harness」**

它明确写了自己不启动 shell、不启动 Claude Code。所以它做不了「批量重构 50 个文件」这类事——它的交互模型是「围绕当前笔记和会话」。

对我们的启示：如果核心场景是批量，就必须自己做批量模式（逐个确认 → 分组确认），这不是加个开关的事，是交互模型的不同。

**取舍三：闭源 + 激活码**

¥99 永久 / ¥19.9 月，绑定本机安装 ID。技术上合理（防白嫖），但对「想把整个库交给它读写」的用户来说，这是一个**无法验证的信任决策**。它声明没有中转服务器、不收集 vault 内容，但这些都只能信，不能验。

对我们的启示：自用项目最大的价值不是省钱，是**代码可读、行为可验证**。

## 3. 与 Copilot 的定位差异

容易混淆，明确划线：

| | Copilot | 本项目 |
|---|---|---|
| 核心交互 | 问问题 → 得到回答 | 提要求 → 文件被改 |
| 主要产物 | 文本 | 变更（diff） |
| 成功标准 | 回答有用 | 文件改对了，且能撤销 |
| 上下文 | 全库检索（RAG） | 明确的文件范围 |

两者不冲突：**用 Copilot 做「问」，用本项目做「改」**。这也是为什么本项目不做全库 RAG。

## 4. 借鉴清单（明确抄什么）

| 来源 | 借什么 | 怎么改 |
|---|---|---|
| Mobie CC | 候选 → 审核 → 写回 | 保留，并加「分块接受」 |
| Mobie CC | 4 类有界记忆文件 | 保留，限制每类 8 KB |
| Mobie CC | 隐私模式（一键关工具） | 保留，做成顶部开关 |
| Mobie CC | 回答带来源引用 | 保留 |
| Smart Composer | 工具调用的 schema 组织方式 | 参考，不照搬 |
| Copilot | 多 provider 配置抽象 | 简化：只做 OpenAI 兼容 |
| Claude Code | 「先读再改」的提示词约束 | 移植到 system prompt |

## 5. 不做什么（防止范围膨胀）

- ❌ 不做全库问答——Copilot 已有且更好
- ❌ 不做 embedding / 向量库——手机算力不允许
- ❌ 不做多用户、不做云端、不做账号
- ❌ 不做插件市场上架（不需要，也过不了）
- ❌ 不做流式（v0.2 前）
- ❌ 不做「自动整理我的整个库」这种一键大爆炸功能——不可控、不可撤销、必然翻车

## 6. 结论

> 本项目不是「更好的 Copilot」，而是**一个窄而深的改库工具**：输入是自然语言指令，输出是可审阅的文件变更。

判断一个需求该不该做，用一句话测试：

> **这件事的产出是「一段文本」还是「一批文件变更」？**
> 前者交给 Copilot，后者才做进本项目。
