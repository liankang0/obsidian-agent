# 06 路线图

原则：**每一期都要能在手机上真实用起来**。不做「半年后一次性交付」。

## M0 骨架（3～5 个晚上）

目标：能在手机上读到笔记、让模型改一次、看到 diff。

| 任务 | 交付 |
|---|---|
| 插件骨架 + esbuild 构建 | `main.js` 能在桌面加载 |
| provider | 能调通一次 `/chat/completions` |
| `read_file` / `patch_file` | 模型能改一篇笔记 |
| DiffModal | 改动先预览，可拒绝 |
| 落盘日志 | 出错能看到原因 |

验收：对着手机说「把这行改成 xxx」，diff 出现，接受后文件真的变了。

风险：`npm install` 与 Obsidian 类型定义版本不匹配；先用官方 sample plugin 的 `package.json` 打底。

## M1 私有可用（1～2 周）

目标：能完成场景 A（批量归一化）和场景 C（单篇深改）。

| 任务 | 说明 |
|---|---|
| `search` / `list_files` / `get_links` / `get_backlinks` | 让模型能自己找文件，而不是靠人给路径 |
| Checkpoint + 续跑 | 杀后台不丢状态 |
| 护栏全集 | 路径越界、`.obsidian` 禁写、大小上限 |
| 批量模式（逐个确认） | 一次 run 处理 N 个文件，每个变更都要点 |
| ~~快照~~（未实现） | 原计划 `state/snapshots/<runId>/` 可回滚；实际落地为 checkpoint + 续跑（见 02-架构设计），「撤销」改为后续工作包里的「按修改记录逆向回放」——WP3 已按此落地（2026-11-12，见 02-架构设计 4.1 与 ADR-010） |
| 设置页 | baseURL / model / key（SecretStorage）/ 温度 |

验收：把 `读书/` 下 20 篇的 tag 统一，中途锁屏杀掉 App，重启后能续跑完成，且可在拒绝后保持原样。

这是**第一个有价值的里程碑**，到这里就应该开始日常使用。

## M2 体验（2～3 周）

| 任务 | 说明 |
|---|---|
| 分块接受 diff | 一段一段地接受，而不是整篇 |
| 状态行 + 进度 | 「正在处理 3/20」 |
| 批量模式的「全部接受同类变更」 | 相同模式的改动一次确认 |
| 错误分类与重试 | 429 退避、401 快速失败 |
| 上下文预算控制 | 超长截断、历史摘要 |
| 手机 UI 打磨 | 底部抽屉、按钮尺寸、键盘遮挡 |

验收：一次处理 20 个文件不再需要 20 次点击（同类变更可批量确认），且整个过程不出现「不知道在干什么」的空窗。

## M3 记忆与个性化（可选，2 周）

| 任务 | 说明 |
|---|---|
| 4 类记忆文件 | Profile / Style / WorkMode / Vault，各有大小上限 |
| 候选记忆 | 先预览再写入，不静默学习 |
| 隐私模式 | 一键关掉全部工具 |
| 语义检索（实验） | 只对「最近 200 篇」建索引，且可关闭 |

验收：用一周后，模型能记住「我叫它写周报时按项目分组、不要用 bullet 套 bullet」这类偏好，且我能查看和删除这些记忆。

## 明确不做（长期）

- ~~上架社区插件市场~~（已推翻：2026-11 起按开源发布流程推进，仓库公开、提交市场；见 README 与 CHANGELOG）
- 多用户 / 云同步 / 账号体系
- 独立的向量数据库
- 自动执行不可撤销的批量操作

## 时间估算的现实修正

上面写的是「理想工时」。按经验，手机端插件开发的实际耗时大概是估算的 2 倍，主要消耗在：

1. 构建与部署链路（每次改代码要重新推包、重载插件）
2. 没有 devtools 的调试
3. Obsidian 移动端的 API 差异（`requestUrl` 行为、文件写入时机）

所以在 M1 之前，先花半天把**部署脚本**做好（构建 → 推到 vault → 提示重载），这是最划算的前置投入。

## 止损条件

如果出现以下任一情况，说明方向要重新评估：

- M0 花超过 3 周仍未在手机上跑通一次改文件 → 换方案（直接买 Mobie CC）
- 手机端 `requestUrl` 调用模型普遍超时 → 说明网络路径有问题，改用电脑端 agent
- 实际使用两周后，发现自己 90% 的需求其实是「问问题」而不是「改文件」 → 项目定位错了，回到 Copilot
